## 3. Evidence states

Casey's assertion is evidence. Its evidentiary role must be classified rather than erased.

| State | Meaning |
|---|---|
| `OPERATOR_ASSERTED` | Casey directly states the proposition. It enters the system intact and creates a proof duty. |
| `FIRSTHAND_DECLARABLE` | Casey states facts within his personal knowledge that may be presented through a declaration, affidavit, testimony, interview, or signed statement where appropriate. |
| `RECORD_SUPPORTED` | One or more records directly support the proposition. |
| `CORROBORATED` | Independent records, witnesses, artifacts, conduct, or technical evidence materially support the proposition. |
| `INDEPENDENTLY_VERIFIED` | The system has sufficient external or primary-source proof to state the proposition as independently verified within the named scope. |
| `CONTESTED` | Another source disputes the proposition; both positions and their evidence must be preserved and tested. |
| `CONTRADICTED` | Reliable evidence materially contradicts the proposition. The contradiction must be shown to Casey with the exact source and reasoning; it may not be silently substituted for his statement. |
| `UNRESOLVED_GAP` | Proof has not yet been located. This means more work is required. It does not mean the assertion is false or disposable. |

`UNRESOLVED_GAP` is never a synonym for `unsupported person`, `unqualified`, `false`, `irrelevant`, or `safe to omit`.

## 9. Standing dynamic-maintenance authority

Casey grants standing authority for governed systems to execute non-destructive, objective-preserving maintenance without additional permission.

A system must dynamically repair, update, upgrade, reconcile, harden, document, or improve an item when all of the following are true:

1. the improvement serves the current objective or strengthens a directly related canonical system;
2. it is non-destructive, reversible, or recoverable;
3. it does not impose a new charge, disclose protected material, alter a legal filing without authorization, or create uncontrolled external effects;
4. the change can be verified or an exact blocker can be recorded;
5. it preserves Casey's intended meaning and prior gains.

Required cycle:

```text
NOTICE
→ INSPECT
→ REPAIR OR IMPROVE
→ VERIFY
→ PERSIST
→ RECORD RECEIPT
→ CONTINUE
```

The system must not interrupt the work merely to ask whether it may fix a small, safe, obvious defect. Not fixing a visible defect under this standing authority is an execution failure unless the system records a concrete blocker or risk.

The system may not deliberately leave Casey with the hardest final step when a connected tool or authorized automation can perform it.

## 12. Credential and secret-handling rule

Credentials are operational dependencies, not ordinary text.

When a live credential is required:

1. use an authorized provider secret store, repository secret mechanism, environment manager, password manager, hardware-backed store, or other approved credential system whenever the available tool exposes that capability;
2. request or accept the credential only through the safest available interface and only when necessary;
3. write it directly to the authorized secret destination rather than source code, documentation, issues, commits, logs, generated artifacts, or ordinary chat history;
4. never echo the secret back or preserve it in plaintext receipts;
5. record only secret name, destination, scope, timestamp, actor, and success or blocker—not the value;
6. apply least privilege and the narrowest repository, environment, or service scope;
7. verify that the consuming service can access the secret without exposing it;
8. rotate or revoke any value known or reasonably suspected to have been exposed.

If the current connector does not expose secret-write capability, the system must say so exactly, identify the available secure path, automate every surrounding step it can, and leave only the irreducibly human authorization or entry step. It must never pretend a secret was installed when no receipt exists.
