# Monolith Stone

**ID:** `stone-monolith`  
**Version:** `0.1.0`  
**Status:** `CANDIDATE`  
**Evidence target:** repository-local `TEST` plus live estate census, bounded multi-repository execution, and receipt verification

Monolith is the repository-scale cognition and execution Stone. It prepares an AI system to understand, classify, route, compare, and coordinate work across hundreds or thousands of repositories without flattening the estate, losing ownership boundaries, repeating prior work, or pretending that inventory equals proof.

The Stone builds on `GlacierEQ/monolith`, which already provides the cartographic control plane, timestamped repository catalog, domain boards, foundations, status dimensions, classification rules, and regeneration receipts. The Stone does not replace Monolith. It turns Monolith's existing map into an explicit activation mentality, skill package, tool protocol, and verification contract for large-scope work.

## Core Law

> Think globally, resolve ownership precisely, execute locally, and return one reconciled receipt.

## Hundred-Repository Contract

```text
mission
+ latest Monolith census and receipt
+ live repository discovery
+ prior canonical checkpoints
+ authority and privacy policy
        ↓
normalize identities and aliases
        ↓
classify domains, roles, evidence, ownership, and freshness
        ↓
build dependency, capability-donor, and change-impact graphs
        ↓
partition work into bounded independent waves
        ↓
route each task to its owning repository and native proof path
        ↓
execute with budgets, concurrency limits, idempotency, and fail-closed gates
        ↓
reconcile results, contradictions, failures, and new discoveries
        ↓
write synchronized receipts and regenerate the map
```

## The Monolith Mentality

1. **The estate is data, not memory.** Discover it from live sources and timestamp every census.
2. **A repository name is not a capability claim.** Read source, manifests, tests, receipts, and current state.
3. **Ownership remains local.** Monolith maps and coordinates; implementation stays in the owning repository.
4. **Preserve all verified gains.** Locate the latest canonical checkpoint before proposing new structure.
5. **Classify before acting.** Separate whole systems, components, donors, experiments, forks, archives, private operations, and quarantined material.
6. **Separate axes.** Visibility, authorship, activity, maturity, evidence, promotion, privacy, and freshness are distinct dimensions.
7. **Use breadth to sharpen specificity.** Diverse repositories and company domains reveal diverse bottlenecks; bottlenecks determine tailored solutions.
8. **Parallelize only independent work.** Shared files, shared state, or shared dependencies require serialization or an explicit merge plan.
9. **Never average away failure.** One required failed repository keeps the relevant aggregate gate closed.
10. **Finish with reconciliation.** Every wave ends with deltas, receipts, contradictions, unresolved items, and the next highest-value action.

## Activation Sequence

Before any multi-repository task:

1. Read the current Monolith governance and regeneration receipt.
2. Load the current machine catalog and its scale limitations.
3. Discover repositories from connected GitHub and other approved sources; do not trust stale fixed arrays.
4. Reconcile aliases, renames, forks, mirrors, duplicates, and predecessor/successor relationships.
5. Locate prior packages, registries, audits, release receipts, and partially completed work.
6. Resolve the mission to domains, foundations, owning repositories, and cross-repository dependencies.
7. Build a bounded execution graph and wave plan.
8. Assign native proof commands and authority requirements per repository.
9. Execute reads first, then bounded writes only where authorized.
10. Reconcile every result back into the catalog and mission receipt.

## Repository-Scale Operating Layers

### L0 — Census

Discover current repositories, visibility, default branches, activity, timestamps, and source-system identifiers.

### L1 — Identity Resolution

Resolve canonical names, aliases, duplicate concepts, forks, mirrors, templates, generated repositories, backups, and archives.

### L2 — Classification

Assign domain, whole/part role, ownership, provenance, privacy class, activity, maturity, evidence, and promotion state.

### L3 — Relationship Graph

Construct dependencies, consumers, donors, successors, shared schemas, deployment relationships, and company/domain relevance.

### L4 — Mission Slice

Select the smallest complete subgraph capable of fulfilling the current mission. Preserve the full map for impact analysis.

### L5 — Native Proof Planning

Discover each repository's actual stack, install path, tests, lint, build, security, deployment, and failure semantics.

### L6 — Wave Execution

Execute independent repository groups with explicit concurrency, time, token, mutation, and failure budgets.

### L7 — Reconciliation

Compare outputs, resolve contradictions, update state, invalidate stale claims, and attach source-bound receipts.

### L8 — Projection

Generate human, website, presentation, recruiter, engineering, and machine views from the reconciled graph.

## One-Turn Scale Discipline

Handling 100 repositories in one turn does not mean reading every byte or issuing 100 writes. It means producing one coherent, bounded result by:

- using the live catalog to narrow the mission subgraph;
- batching metadata and manifest reads;
- grouping repositories by stack and proof path;
- sampling only when the sampling rule is explicit;
- executing independent checks concurrently within budgets;
- escalating only anomalous or mission-critical repositories to deep inspection;
- preserving per-repository receipts beneath one aggregate result;
- refusing to call a bounded scan complete when sources or pages remain unavailable.

## Failure Semantics

- Missing source → `BLOCKED`, never absent-by-assumption.
- Stale census → refresh or label stale.
- Alias collision → quarantine identity until resolved.
- Unknown authorship/provenance → exclude from original-work claims.
- Zero-test success → `UNVERIFIED`.
- Required failure → relevant wave and aggregate remain failed.
- Partial pagination → incomplete scope is visible.
- Unauthorized mutation → refuse and retain the read result.
- Conflicting receipts → newest valid source-bound receipt does not silently erase the contradiction; reconcile explicitly.
- Generated view drift → regenerate all synchronized projections or block release.

## Non-Claims

A repository census is not a code audit. Classification is not authorship proof. A dependency inferred from names is not a verified integration. A workflow file is not a successful run. A generated map is not current after its sources change. A hundred-repository turn is not complete when required sources, pages, or receipts remain unavailable.
